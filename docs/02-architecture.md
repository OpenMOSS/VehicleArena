# 系统架构与执行边界

[English version](en/architecture.md)

VehicleArena 让多个主体在同一个持续运行的交通世界中决策。道路运动与碰撞由 SUMO 执行，车内设备由 `VehicleWorld` 执行；模型只能提出请求，不能直接改写车辆位置、碰撞或任务完成状态。

![共享三维环境、Agent 角色与事件时间线](assets/paper-architecture.png)

图中分别展示共享交通世界、三个 Agent 的职责，以及乘客请求、驾驶唤醒和验收在同一仿真时间线上发生的关系。图中的截图用于说明观测形式，不代表每辆车都安装了全部传感器。

## 各层职责

- Driving Agent 根据本车观察决定速度、制动、换道、路口方向及车内操作；Personal Agent 代表乘客提出即时或延时请求；Judge 独立检查请求是否在真实轨迹中完成。PA 请求会交付给 DA，Judge 的检查本身不提供驾驶控制机会。
- `MultiSimEngine` 维护一个共享 SUMO 世界。每个 `0.1 s` 物理步推进车辆、行人、信号交互和碰撞；背景交通由 SUMO 原生控制，选定车辆可由独立的 LLM 驾驶。
- `VehicleWorld` 为每辆车维护独立的装备和座舱状态。场景 JSON 冻结地图、初态、参与者和预设事件；评测读取轨迹、工具回执和请求证据，不反写世界状态。

DA 的工具调用先经过能力和参数校验。驾驶控制提交给 SUMO，车内操作交给对应模块；后续观察和评分都以实际状态为准，而不是以模型的意图或文字声明为准。Web3D 车内画面和可选的局部几何图从同一冻结物理状态渲染；导航小地图只给路线建议，不替 DA 转向。

更大的观测示例及其信息边界见[导航小地图](navigation-progress.md)和[可选局部几何图](web3d-lidar-bev.md)。

全局调试图和 `sumo-gui` 截图只用于检查仿真，不能替换 DA 的局部观察，否则会泄露感知范围外的信息。地图内行人沿人行道或斑马线运动，不接受任意坐标的自由路径。

## 扩展选择

- “车里多一个能力”使用车辆模块。
- “同一物理车辆换一种驾驶模型”更换该 LLM 角色的模型配置。
- “车辆尺寸、动力或装备不同”使用能力档案。
- “场景里出现一种领域角色”使用运行实体适配器。
- “按某种难度规律批量造场景”使用场景层。
- “新增车内操作的约束和验收条件”使用 YAML 规则。

不要在 `TrafficCoordinator` 中为某个测试场景按 ID 写分支，也不要在物理层实现“所有车都完美避让”的宏观策略。公共物理规律放在 SUMO 执行层；待评行为来自每个 LLM 角色，背景交通行为来自 SUMO。
